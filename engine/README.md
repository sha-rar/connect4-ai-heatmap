# Connect 4 engine (C++)

Standalone C++20 engine that implements the [`chooseMove()` contract](../docs/api.md). It has no dependencies and does not need the website. The website runs it as WebAssembly in a Web Worker.

## Build, test and benchmark

Requires CMake 3.20+ and a C++20 compiler (GCC 11+, Clang 14+ or MSVC 2022).

```sh
cmake -S engine -B engine/build
cmake --build engine/build
ctest --test-dir engine/build --output-on-failure   # or: engine/build/connect4_tests [filter]
engine/build/connect4_bench [--max-depth N] [--runs N]
```

**Windows with MSYS2:** put `C:\msys64\ucrt64\bin` first on `PATH` before configuring, otherwise other DLLs on `PATH` can stop `g++` from running. Use the `MinGW Makefiles` generator:

```sh
export PATH=/c/msys64/ucrt64/bin:$PATH
cmake -S engine -B engine/build -G "MinGW Makefiles"
```

The MinGW runtime is linked statically, so the built executables run without MSYS2 on `PATH`.

Build options: `-DCONNECT4_BUILD_TESTS=OFF`, `-DCONNECT4_BUILD_BENCH=OFF`. Tests and the benchmark read `tests/fixtures/*.json`; set `CONNECT4_FIXTURES` to use another directory.

## WebAssembly build

The website uses `apps/web/src/engine/generated/connect4.{js,wasm}`. These files are committed, so the app builds without Emscripten. Rebuild them after changing the engine:

```sh
# Activate the Emscripten SDK first (emsdk_env), then:
pnpm build:wasm
```

`scripts/build-wasm.mjs` runs `emcmake cmake` into `engine/build/wasm` (using MinGW Makefiles on Windows, or `CMAKE_GENERATOR` if set) and copies the output into the web app. Built and tested with Emscripten 6.0.13.

**Git Bash on Windows:** `emsdk_env.sh` does not set up the environment there. Set it by hand:

```sh
export EMSDK=C:/Users/<you>/emsdk EM_CONFIG=C:/Users/<you>/emsdk/.emscripten
export PATH=$EMSDK:$EMSDK/upstream/emscripten:$PATH:/c/msys64/ucrt64/bin   # mingw32-make
```

The module exposes a small C ABI from [`wasm/bindings.cpp`](wasm/bindings.cpp). JavaScript writes the 42 cells into an `Int32` buffer, calls `c4_choose_move(cells, player, depth, timeLimitMs, result)`, and reads 17 `Int32` values back. The layout is documented in the source and decoded by [`wasmEngine.ts`](../apps/web/src/engine/wasmEngine.ts). Both sides check the size with `c4_result_size()`. One engine instance, with a 16 MiB transposition table, lives for the lifetime of the worker.

The module is built for `web,worker,node`, so `tests/web/wasm.test.ts` can run the WASM engine against the shared fixtures under Vitest. Because of this, Vite warns that `node:module` was externalized; that code path never runs in the browser.

## Layout

| Path | Contents |
| ---- | -------- |
| `include/connect4/position.hpp` | Bitboard `Position`: moves, validation, win detection, contract conversion |
| `include/connect4/evaluate.hpp` | Static evaluation, a port of `apps/api/src/engine/evaluate.ts` |
| `include/connect4/tt.hpp` | Fixed-size transposition table |
| `include/connect4/search.hpp` | `Engine::chooseMove()`: alpha-beta with iterative deepening |
| `wasm/bindings.cpp` | C ABI exported to JavaScript (also compiled into the native tests) |
| `support/` | Minimal JSON reader and fixture loader (tests and benchmark only) |
| `tests/` | Dependency-free test harness and tests |
| `bench/` | Benchmark, mirrors `apps/api/bench/benchmark.ts` |

## Design

**Bitboards.** A position is two `uint64_t`s: the discs of the player to move and all discs. Each column takes 7 bits (6 cells and one spare bit), so a move is one addition and four-in-a-row is four shift-and-mask tests. The spare bit stops alignments wrapping from one column into the next. `current + mask` is a unique 49-bit key.

**Evaluation.** Same weights and windows as the TypeScript engine, using precomputed masks for the 69 possible lines and `popcount`. `tests/fixtures/evaluations.json` (generated by `pnpm --filter @connect4/api export:evaluations`) checks the two give identical scores on 215 positions.

**Search.** Negamax with alpha-beta pruning, centre-first move ordering, and the shared score scale (`WIN_SCORE - plies` for wins). The evaluation favours the root player and is not symmetric between the two players, so leaves are always scored for the root player and the sign is flipped for the opponent. Every root column is searched with a full window, so the heatmap gets exact values rather than bounds.

**Iterative deepening.** Depths 1, 2, … run until the requested depth, the end of the game, or the time limit. An iteration interrupted by the time limit is thrown away, and its partial subtrees are never written to the table. `usedDepth` is the deepest finished iteration, and all `columnScores` come from it. Depth 1 always completes, so there is always a legal move.

**Transposition table.** 2^20 entries of 16 bytes (16 MiB) by default, using Fibonacci hashing and depth-preferred replacement. Each `chooseMove()` starts a new generation, and only entries from the current one are used. Within one search, a position's ply from the root is fixed by its disc count, so stored mate scores need no adjustment, and cached results match plain minimax exactly. The tests check this against an unpruned reference search.

## Differences from the TypeScript engine

- No opening book or win/block shortcuts. The search finds immediate wins and forced blocks itself, so every legal column always gets a score and a forced block is never reported as a win.
- `usedDepth` is the completed depth, not the requested one, and the requested depth is capped at the number of empty cells.
- Results never include scores from an interrupted search.
